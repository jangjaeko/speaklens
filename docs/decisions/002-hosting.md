# 002. Host on Render (Docker web service + Render Postgres)

- **Status:** Accepted
- **Date:** 2026-10-27

## Context

SpeakLens needs, in production:

- A long-running Rails process (Puma) and a **Solid Queue worker** that keeps polling for
  jobs. STT and LLM calls run in background jobs and take tens of seconds.
- Turbo Streams over Action Cable (long-lived connections) for live status updates.
- PostgreSQL.
- An always-on demo URL for interviewers. A one-minute cold start on the first click is
  not acceptable.

The goal is a working deploy in week 1 with minimal ops work.

## Options considered

| Option | Verdict |
|---|---|
| **Vercel** | Rejected. Serverless functions only run per request: there is nowhere for a Solid Queue worker to live, no official Ruby runtime, and long-lived connections are a poor fit. |
| **Render free tier** | Rejected. Web services sleep after 15 min idle (~1 min cold start), and free Postgres is deleted 30 + 14 days after creation. |
| **Render free web + Neon free Postgres** | Viable for $0, but the cold start remains. Not worth saving ~$13/month during a job search. |
| **Kamal + VPS** | Rails 8's default and cheapest at steady state, but costs days of server setup. Revisit later if desired. |
| **Fly.io / Railway / Koyeb** | No meaningful free tier for an always-on Rails app; no advantage over Render for this project. |
| **Render paid (chosen)** | Starter web (0.5 CPU / 512 MB, ~$7/mo) + Postgres 0.1c-256mb (~$6/mo). |

## Decision

Deploy to **Render** using a **Blueprint** (`render.yaml`) so the infrastructure is
reviewable in the repo.

- **Docker runtime** with the Dockerfile generated by `rails new`. This avoids depending
  on Render's native Ruby version support (we use Ruby 4.0.9) and keeps local and
  production images identical.
- **`dockerCommand: ./bin/rails server`**: Render routes traffic to `$PORT` (10000).
  Puma already binds to `$PORT`. The Dockerfile's default CMD runs Thruster on port 80 in
  front of Puma on 3000, which does not line up with Render's port. Render's edge already
  handles TLS and HTTP/2, so we skip Thruster here.
- **`preDeployCommand: ./bin/rails db:prepare`** runs migrations once per deploy, before
  traffic switches to the new version.
- **`SOLID_QUEUE_IN_PUMA=true`** runs the job supervisor inside Puma, so one web service
  covers both HTTP and jobs. **`WEB_CONCURRENCY=1`** keeps memory within 512 MB.
- **`autoDeployTrigger: checksPass`** deploys only after CI passes.
- `config.assume_ssl` / `config.force_ssl` are enabled because Render terminates TLS in
  front of the app.

### Databases: Rails 8 defaults, one Postgres instance

Rails 8 uses four databases in production: `primary`, plus `cache`, `queue`, and `cable`
for Solid Cache / Solid Queue / Solid Cable. We keep that layout (convention over
configuration) and put all four databases in **one** Render Postgres instance.

Render provides a single `DATABASE_URL`. `config/database.yml` derives the other three
URLs by swapping the database name at the end of that URL. This is the same approach
Render documents for adding databases to an instance. `db:prepare` creates any missing
databases. If the database user lacks permission to do that, create them once by hand
with `CREATE DATABASE`.

We could not simply set `database:` next to `url:`: in Rails, values parsed from `url`
override the individual keys, so the URL's database name would win.

### Audio file storage: local disk, short-lived

Render's filesystem is ephemeral: it is wiped on every deploy and restart. We keep
Active Storage on the `:local` service anyway, because audio only needs to exist until
transcription finishes (seconds to minutes). The original audio is then deleted, which
is also a privacy feature (CLAUDE.md §7).

- **Trade-off:** If a deploy happens mid-transcription, that recording's job fails and is
  shown as failed. The user re-records. This is acceptable for the MVP.
- **Move to S3-compatible storage (e.g. Cloudflare R2) when** we run more than one
  instance (the web instance that received the upload and the instance running the job
  could differ), or when we add a feature that keeps audio long-term.

## Consequences

- Cost: ~$13/month while the demo is live. Delete the services when no longer needed.
- Running Solid Queue inside Puma means a slow job competes with web requests for the same
  process. If that becomes a problem, split out a Render background worker running
  `bin/jobs`.
- The Kamal config generated by `rails new` is removed to avoid two competing deploy
  setups. The Dockerfile stays.
